# План: сигналы, задержки, уверенность, тишина, интерфейсы CLI и веб

Файл для агентов и моделей, которые продолжают работу без истории обсуждения. Здесь
условие кейса, текущее состояние кода, принятые решения с причинами и пошаговый план.

Команда пользователя «реализуй шаг N» означает: выполнить шаг N из раздела «План», и
только его. Перед работой прочитать файл целиком.

## Правила работы

Обязательны для любого шага.

- **Никаких fallback.** Неверный вход вызывает исключение: `ValueError`, а для
  отсутствующего ключа JSON — `KeyError`. Обходных путей «если не вышло, то…» нет.
  Значения по умолчанию допустимы только там, где они описаны в этом файле: настройка
  шага или сценария, не заданная явно, берётся уровнем выше, вплоть до корня правил.
- **Тесты не трогать.** Не менять и не писать тесты, пока пользователь явно не
  попросит. Сейчас `uv run pytest` падает уже при сборке `tests/test_engine.py` с
  `ValueError: сценарий 'свет в ванной': неизвестные ключи ['pattern']`: тесты отстали от
  API (время, `patterns` из шага 1, строгие ключи JSON и граф из шага 3, обязательный
  `min_score` из шага 4, `min_confidence` и `Match.confidence` из шага 5, `Scenario.order` и
  `render` с шаблонами `any` из шага 6, `rule_engine.cli` и `render` из шага 8). Это известно,
  без просьбы не чинить. Правило про примеры ниже
  к тестам не относится (решение пользователя).
- **Вход идеальный.** Токены уже обработаны и нормализованы, метки времени точные.
  Задержек распознавания и опоздавших токенов нет. Не предлагать нормализацию,
  стемминг, исправление опечаток, буферы переупорядочивания, запас на опоздание.
- **Если неясно — спросить.** Если решение здесь не описано, задать пользователю
  вопрос с вариантами (опрос), рекомендованный вариант первым, и не угадывать.
  Принятые решения ниже без просьбы не пересматривать.
- **Язык.** Пользователь пишет по-русски. Комментарии, сообщения ошибок, README и
  примеры — на русском.
- **Стиль.** Как в текущем коде: `dataclass(frozen=True)`, `NamedTuple`, короткие
  комментарии на русском, токен в сообщениях ошибок выводится через `!r`.
- **Коммитить только по просьбе.** Без просьбы пользователь коммитит сам. Сообщение —
  очень короткое, в стиле прошлых коммитов (`feat: ...`), без строки соавторства агента.
- **После шага.**
  - Обновить README (правила прохода, форматы, граф, примеры) и файлы в `examples/`,
    чтобы `uv run rule-engine ...` показывал новое поведение.
  - Примеры (решение пользователя): у каждого шага — свой файл потока, по которому
    понятно нововведение. Старые примеры, и `.json`, и `.txt`, должны запускаться. Если
    нововведение меняет поведение старого примера, пример меняется вместе с ним, а не
    сохраняется в прежнем виде.
  - Проверить запуском CLI. Временные скрипты держать вне репозитория.
  - Отметить шаг в этом файле как сделанный: `[x]`.
- **Отчёт пользователю.** Коротко, с ASCII-графом и трассой прохода в стиле README.

## Кейс

Studcamp, «Детектор составных событий». Нужен движок правил над готовым потоком токенов
с уверенностью (score); аудиоклассификатор и микрофон вне рамок задачи.

Требования:

1. Несколько правил с общим началом срабатывают на одном потоке.
2. События на границе порций не теряются: поток можно подавать кусками.
3. У правил есть версии, и старые совпадения сохраняют связь со своей версией. В этот
   план требование не входит.

Команда должна решить:

- что значит отсутствие события в окне;
- как ограничить число активных частичных совпадений;
- когда вступает в силу новая версия правила.

Запуск:

```bash

uv run rule-engine run examples/smart_home.json examples/stream.txt   # 8 сценариев
uv run rule-engine run examples/smart_home.json examples/pause.txt    # 2 сценария
```

Текущая семантика:

- Сценарии собираются в бор (префиксное дерево), у сценариев с общим началом общие
  вершины.
- Токен без подходящего ребра пропускается, совпадение ждёт дальше
  (skip-till-next-match).
- Совпадение, пройдя по ребру, **переходит** в следующую вершину, а не копируется.
- В вершине живёт одно совпадение; из двух остаётся то, что началось позже. Поэтому
  активных совпадений не больше, чем вершин.
- Сценарий срабатывает при входе в свою конечную вершину. Если у вершины есть дети,
  совпадение остаётся активным.
- Пауза между соседними токенами потока больше `max_gap` снимает все частичные
  совпадения.
- Время, идущее назад, — ошибка. Токен вне словаря — ошибка. Score хранится, но не
  используется.
- `Step.position` — сквозной номер события в потоке, между порциями не сбрасывается.

Текущие форматы:

- JSON: `{"max_gap": 3.0, "vocabulary": [...], "scenarios": [{"name": ..., "pattern":
  "токены через пробел"}]}`.
- Поток: одна строка на событие, `токен уверенность время`. Пустые строки и строки,
  начинающиеся с `#`, пропускаются.
- `Event.time` — абсолютное время в секундах. Его ставит детектор, шкала одна на весь
  поток: в работе Unix time, в примерах — отсчёт от начала записи.

Известные недочёты. Без просьбы не исправлять:

- `feed` теряет совпадения, найденные до исключения в той же порции;
- граница «ровно `max_gap`» на float плавает: `4.4 − 1.4 = 3.0000000000000004`;
- граница «ровно `min_confidence`» тоже: √(0.49·0.64) = 0.56, а во float
  `0.5599999999999999`, и при пороге 0.56 сценарий не срабатывает;
- в графе в README нет ветки «включи → чайник»;
- кривой JSON даёт голый `KeyError`.

## Новый сценарий: сигнализация

Хозяин заходит тихо, и система понимает, что это он: «хозяин пришёл». Взлом — это
одно из трёх:

- дверь открыли громко: `<дверь>` и `<громкий звук>` в любом порядке;
- пришёл `<громкое открывание двери>`;
- пришёл `<стекло разбилось>`.

Тогда нужно включить сигнализацию и вызвать полицию. Подобных сценариев может быть много.

Особенности сигналов:

- между нужными сигналами может прийти лишний, у которого есть своё ребро в боре: он
  шаг другого сценария;
- сигналы могут приходить в любом порядке;
- сигналы разнесены во времени, и у сценария может быть своя задержка;
- сигнал может быть неуверенным, то есть иметь малый score.

## Принятые решения

Решения приняты с пользователем в опросах. Не пересматривать.

### Р1. Сигналы — обычные токены в `< >`

`<дверь>`, `<громкий звук>`, `<шаги>`, `<громкое открывание двери>`,
`<стекло разбилось>`. Скобки — соглашение в JSON, и оно может поменяться. Движок скобки
не разбирает: для него токен — непрозрачная строка.

Сказанное «дверь» и звук `<дверь>` — разные токены. Иначе громко сказанное «закрой
дверь» стало бы взломом.

### Р2. Шаблон — список токенов, у сценария есть альтернативы

В токенах бывают пробелы, поэтому шаблон — список в JSON, а не строка через пробел.

У сценария есть `patterns` — список альтернатив. Сработала любая — сработал сценарий
с этим именем.

В строке потока токеном считается всё до двух последних чисел:
`<громкий звук> 0.62 12.4`.

### Р3. Копия вместо перехода, без откатов

Пройдя по ребру, совпадение **остаётся** и в старой вершине. Это семантика
skip-till-any-match, как `followedByAny` во Flink CEP. Без копии лишний токен со своим
ребром уводит совпадение в чужую ветку:

```
«кто-то вошёл» = <дверь> <шаги>,  «взлом» = <дверь> <громкий звук>

переход (сейчас):
#1 <шаги>          ●═<дверь>═>( )─┬═<шаги>═════════>( ) ✓ «кто-то вошёл»
                                  └─<громкий звук>─>( )   совпадение ушло из <дверь>
#2 <громкий звук>  ●─<дверь>─>( )─┬─<шаги>─────────>( )
                                  └─<громкий звук>─>( )   ✗ «взлом» потерян

копия (нужно):
#1 <шаги>          ●═<дверь>═>(*)─┬═<шаги>═════════>( ) ✓ «кто-то вошёл»
                                  └─<громкий звук>─>( )   копия ждёт в <дверь>
#2 <громкий звук>  ●═<дверь>═>(*)─┬─<шаги>─────────>( )
                                  └═<громкий звук>═>( ) ✓ «взлом»
```

Откаты отклонены. Откат — это вернуться назад по потоку и перечитать токены по другой
ветке. Для этого пришлось бы хранить прошлые токены, сломалась бы работа порциями, а в
худшем случае число перечитываний растёт экспоненциально. Копия даёт тот же результат
без возврата.

Совпадений по-прежнему не больше одного на вершину. Это меняется в Р7.

### Р4. Повторы: правило и cooldown

С копиями сценарий может сработать повторно на тех же токенах. Примеры: «выключи свет
свет»; `<дверь> <громкий звук> <дверь>` при любом порядке.

- **Всегда:** сценарий не срабатывает на совпадении, у которого есть общий токен с его
  прошлым выданным срабатыванием. Токены сравниваются по позиции в потоке.
- **`cooldown` у сценария** (секунды, по умолчанию 0): после срабатывания сценарий
  молчит. Три `<стекло разбилось>` подряд дают одну тревогу.
- **Заглушённое cooldown срабатывание** не занимает токены и не продлевает cooldown.
  Пока сигналы идут, тревога повторяется раз в cooldown: `<стекло разбилось>`@0 ✓;
  `<дверь>`@58 `<громкий звук>`@59 — молчим; `<громкий звук>`@61 ✓ по `<дверь>`@58.
- **`cooldown` — настройка сценария в JSON, а не свойство токенов.** Все токены движок
  обрабатывает одинаково (Р1). Cooldown ставит автор правил. В примерах он есть только у
  «взлома»: у команды он заглушил бы настоящий повтор.

### Р5. Задержка — между шагами сценария

Срок жизни совпадения — время его последнего шага плюс задержка следующего шага.

Общий сброс по тишине в потоке убирается. Посторонние токены между шагами больше не
продлевают совпадение.

Задержка шага берётся у самого шага. Если её там нет — у сценария, если нет и там —
`max_gap` из корня правил.

### Р6. Ребро бора = токен + задержка + порог

> [!WARNING]
> **КОМАНДЕ: РЕШЕНИЕ Р6 НУЖНО ПЕРЕСМОТРЕТЬ В БУДУЩЕМ.**
> Пометка для участников команды, а не для агента. Агент реализует Р6 как написано и
> без просьбы пользователя его не пересматривает.

Шаги с разными настройками — разные рёбра, даже если токен у них один. Сценарии делят
общее начало, только если настройки на нём совпадают. Иначе правило «в вершине держим
лучшее совпадение» теряет срабатывания:

```
S1 = A B C, задержка 1 с;  S2 = A B C D, задержка 10 с;  общая ветка A→B→C
поток: A@0.0  B@0.9  B@1.2  C@1.5

в вершине B:  X = A@0.0 B@0.9   подходит и S1, и S2
              Y = A@0.0 B@1.2   подходит только S2 (1.2 > 1), но свежее
оставить Y → на C@1.5 сценарий S1 потерян
оставить X → для S2 хуже: истечёт раньше

с ветвлением:  ●─A─>( )─┬─B [1 с]──>( )─C [1 с]──>( ) S1
                        └─B [10 с]─>( )─C [10 с]─>( )─D─>( ) S2
```

Худший случай — у каждого сценария свои настройки. Тогда бор вырождается в набор
отдельных цепочек, но это не хуже, чем без бора вообще.

### Р7. Две уверенности

**Порог токена `min_score`.** Шаг принимает токен, только если `score ≥ min_score`.
Если ниже, для этого ребра токена нет, и совпадение ждёт дальше; другое ребро с меньшим
порогом может его принять. Порог берётся у шага, потом у сценария, потом из корня.
Порог входит в ключ ребра (Р6).

**Общая уверенность** — среднее геометрическое score шагов: `(s1·…·sk)^(1/k)`.
Сценарий срабатывает, если она `≥ min_confidence`. Порог берётся у сценария, если его
нет — из корня. Уверенность выдаётся в результате.

Почему среднее геометрическое:

- **Произведение** наказывает длину. Шесть токенов по 0.9 дают 0.53, так что один
  стандартный порог для фраз разной длины не работает.
- **Арифметическое среднее** позволяет сильному сигналу перекрыть слабый.
  `<дверь> 0.95` + `<громкий звук> 0.35` дают 0.65, хотя взлом отличает именно звук.
- **Среднее геометрическое** от длины не зависит и сильнее тянет вниз слабый токен: в
  том же примере 0.58.

Следствия:

- Если порог токена m, среднее геометрическое не меньше m. Поэтому общий порог имеет
  смысл, только если он выше порога токена.
- **Ранний отсев.** Частичное совпадение выбрасывается, если даже при score 1.0 у всех
  оставшихся шагов оно не дотянет до порога ни одного сценария, достижимого из его
  вершины. Оценка сверху для сценария длины L: `(s1·…·sk)^(1/L)`.
- **Несколько совпадений в вершине.** В вершине (и в состоянии из Р8) теперь может
  стоять несколько совпадений: свежее против более уверенного. Держим все несравнимые.
  A вытесняет B, только если A не старее (позиция последнего шага у него ≥) и не менее
  уверенно (произведение у него ≥). Искусственного предела на их число нет.

```
«взлом»: задержка 5 с, min_score 0.3, min_confidence 0.6
#0 <дверь> 0.9 @0.0   (*) [0.9, до 5.0]
#1 <дверь> 0.4 @2.0   (*) [0.9, до 5.0]   увереннее
                          [0.4, до 7.0]   живёт дольше
<громкий звук> 0.8 @4.0 → √(0.9·0.8) = 0.85 ✓   (по второму было бы 0.57 ✗)
<громкий звук> 0.8 @6.0 → первое истекло, второе даёт 0.57 ✗
```

### Р8. Порядок задаётся в сценарии; «любой порядок» — на подмножествах

У сценария `"order"`: `"sequence"` (по умолчанию) или `"any"`. Для `any` задержка тоже
считается между шагами, то есть между соседними по времени сигналами набора.

Сопоставитель для `any` отдельный, не бор. Состояние частичного совпадения: набор уже
собранных токенов, время последнего шага и уверенность. Разные порядки прихода попадают
в одно состояние:

```
{<дверь>}           {<шаги>}           {<голос>}
{<дверь>,<шаги>}    {<дверь>,<голос>}  {<шаги>,<голос>}
{<дверь>,<шаги>,<голос>}  ✓
```

Состояния создаются только тогда, когда до них доходит поток. В худшем случае на шаблон
приходится 2ⁿ − 1 состояний. Это цена точной семантики, искусственных пределов не
ставить.

Отклонены: перестановки в боре (n! путей) и предел на длину набора.

### Р9. Отсутствие события и таймер

«Хозяин пришёл» — это `<дверь>`, после которой 3 с нет ни `<громкий звук>`, ни
`<стекло разбилось>`. Это и есть ответ на вопрос кейса, что значит отсутствие события
в окне.

Шаг-тишина ставит совпадение на таймер. Запрещённый токен со score не ниже порога,
пришедший в окне, снимает совпадение. Если окно прошло без него, шаг выполнен.

```
#0 <дверь>         @0.0   «хозяин пришёл»: тишина до 3.0
   время > 3.0            ✓ «хозяин пришёл»

#0 <дверь>         @0.0   «хозяин пришёл»: тишина до 3.0
#1 <громкий звук>  @0.8   ✗ тишина нарушена;  ✓ «взлом»
```

- **Время.** Его двигают события и вызов `advance(t)`.
- **Таймер в отдельном потоке** (решение пользователя). Он ждёт ближайший срок по
  часам и вызывает `advance`.
- **Ядро движка остаётся детерминированным:** `push`, `advance`, `next_deadline`.
  Таймер-поток и `push` защищены одной блокировкой.
- **Callback.** Срабатывания по таймеру отдаются через callback, потому что у таймера
  нет вызывающего.
- **Прогон файла (CLI).** Потока нет: время двигают метки времени в файле потока.
  Иначе файл с отсчётом от 0 пришлось бы проигрывать в реальном темпе.
- **Тишина до двери.** Её проверяем тоже: порядок сигналов не важен, и звук может
  прийти чуть раньше двери.

### Р10. Ахо–Корасик отклонён, бор остаётся

Ахо–Корасик — это бор плюс суффиксные ссылки. Он держит одно состояние: самый длинный
конец прочитанного, с которого начинается какой-нибудь шаблон. Поэтому он находит
только непрерывные вхождения.

Почему он не подходит:

- **Общий фильтр.** Если заранее убрать токены, которых нет ни в одном шаблоне, это
  поможет со словами «и» и «пожалуйста». Но лишний токен со своим ребром так не убрать:
  `<шаги>` между `<дверь>` и `<громкий звук>` нужен сценарию «кто-то вошёл». После
  `<дверь> <шаги>` автомат забывает, что дверь уже была.
- **Фильтр на каждый сценарий.** Это уже не один проход для всех шаблонов. К тому же
  совпадение рвут повторы своих же токенов: `<дверь> <шаги> <шаги> <голос>`.
- **Проверка поверх.** Время так проверить можно, а порог уверенности — нет. Проверка
  поверх умеет только отказать, а нужно пропустить токен и ждать дальше.
- **Итог.** Чтобы автомат помнил `<дверь>` после `<шаги>`, нужно держать несколько
  состояний. Тогда суффиксные ссылки уже не нужны, и получается ровно наш бор плюс
  набор активных совпадений.

### Р11. Слои: домен, сценарии использования, интерфейсы

Пользователь выбирает между CLI и веб-версией, поэтому интерфейс вынесен в отдельный слой
(решение пользователя).

```
main.py — точка сборки: rule-engine cli … | rule-engine web …
   ├─> interfaces/cli ─┐   argparse, текст
   └─> interfaces/web ─┤   контроллер, презентер (HTML, SVG); server.py — FastAPI
                       ▼
                application/   RuleEngineService, view-модели, формат потока
                       ▼
                   domain/     rules, graph, unordered, engine
```

- **Зависимости только вниз.** Домен не знает о сценариях использования, сценарии — об
  интерфейсах и фреймворке, CLI и веб — друг о друге.
- **Взаимозаменяемость — через общий слой.** CLI и веб — два независимых адаптера над
  `RuleEngineService`. Общего презентера у них нет: CLI пишет в stdout по ходу прогона, веб
  отвечает HTML на запрос. `Interface.run(argv)` — только контракт для выбора в `main.py`.
- **Паритета возможностей нет.** У веба есть плеер по кадрам, у CLI — нет. Каждый
  интерфейс берёт из `RuleEngineService` то, что ему нужно.
- **Абстракция — когда есть вторая реализация.** Из DDD взяты только слои. Репозиториев нет:
  правила и поток приходят в `RuleEngineService` текстом, откуда его взять, решает интерфейс.
  Порт появляется вместе со второй реализацией: `LiveListener` — на шаге 10.
- **View-модели — чистые данные.** Интерфейсы не видят объектов домена: один `GraphView` CLI
  печатает деревом, веб рисует в SVG. Поэтому `render` уходит из домена в CLI.

### Р12. Веб: рендер на сервере, тонкий слой фреймворка

- **HTML собирает сервер** (решение пользователя): шаблоны Jinja2, граф — SVG, раскладку
  дерева считает Python. Своего JavaScript — один небольшой файл без библиотек и без CDN.
- **Фреймворк знает только `server.py`.** Там маршруты, разбор формы, статика и запуск
  uvicorn. Контроллер принимает и отдаёт строки, поэтому замена FastAPI — правка одного
  файла.
- **Зависимости веба обязательные** (решение пользователя): `uv sync` ставит всё сразу.
- **Прогон отдаётся целиком.** Сервер прогоняет поток один раз и присылает все кадры,
  ползунок переключает их на клиенте без запросов.

### Р13. Живой режим

Нужен таймер тишины из шага 7 (`LiveEngine`), поэтому делается после него.

- **WebSocket**, на соединение — свой `LiveEngine`. Первое сообщение задаёт правила, дальше
  идут токены; ответы — HTML-фрагменты.
- **Время ставит движок под блокировкой** (`LiveEngine.push_now`). Если ставить его до
  блокировки, таймер может успеть сдвинуть время вперёд, и событие окажется в прошлом.
- **Снимок отдаётся вместе со срабатываниями.** `LiveEngine` после каждого события и хода
  таймера отдаёт `Update`: срабатывания и снимок совпадений, взятый под той же блокировкой.
  Иначе более старый снимок мог бы прийти после нового.
- **Callback таймера вызывается из его потока.** Мост в asyncio
  (`loop.call_soon_threadsafe`) — забота `server.py`.

### Р14. Отказы записывает движок

Чтобы было видно, почему токен не сработал, движок на каждом событии записывает отказы
(`Engine.misses`): порог токена, опоздание, снятие по сроку, ранний отсев, общая уверенность,
повтор, cooldown (решение пользователя: должно быть понятно, мешает уверенность или
задержка). Интерфейс только показывает их словами: правила прохода знает один движок, и
повторять их в презентере значило бы держать вторую копию, которая разойдётся с первой.

### Р15. Динамическое добавление сценария

По просьбе пользователя добавлен `Engine.add_scenario(Scenario | dict)`. Пользователь
уточнил: нужна простая вставка в общий бор, без разделения совпадений на поколения.
Сохранившиеся префиксы могут продолжаться по добавленным веткам. Стандартные настройки
остаются исходными; словарь расширяется токенами успешно добавленных сценариев.

- Добавление `sequence` дописывает недостающие вершины за обход шагов нового сценария.
  Идентичность существующих `Node` сохраняется; полный граф не перестраивается.
- Формат `Node`, `Partial`, алгоритм `push`, снимки и вытеснение не меняются. Конечная
  вершина по-прежнему хранит один `scenario`. Поддержка нескольких сценариев с полностью
  одинаковым шаблоном не входит в задачу; прежние проверки дубликатов сохраняются.
- Добавление `any` собирает только новые наборы; индекс владельцев сохраняет прежнюю
  проверку дубликатов без перебора всех существующих шаблонов.
- Имя сценария остаётся уникальным. Настройки и дубли шаблонов проверяются до изменения
  движка. Ошибка не занимает имя и не меняет граф или словарь. Новые токены собираются
  из всех альтернатив и шагов-объектов; исходные дополнительные слова сохраняются.
- Прошлые события не переигрываются; завершённые и ранее отброшенные совпадения не
  восстанавливаются. У нового набора `any` нет накопленных шагов.
- Это добавление новых сценариев между вызовами движка. Изменение и удаление правил,
  полные версии правил и одновременные вызовы из нескольких потоков не реализованы.

### Р16. Порядок срабатываний одного события и ничья при выборе

Раньше оба исхода давал порядок обхода словаря всех активных совпадений. Ускоренный проход
(дополнение «Ускорение прохода») этот словарь не обходит, поэтому правила заданы явно
(решения пользователя):

- **Порядок.** Если на одном событии сработали несколько сценариев, первым выдаётся начавшийся
  раньше, при равном начале — объявленный раньше. На всех примерах это прежний вывод:
  «утро» перед «чайник: разогреть», «ухожу из дома» перед «дверь: закрыть».
- **Ничья.** Из совпадений одного сценария с равной уверенностью и равным началом выдаётся
  то, у которого шаги позже: позиции шагов сравниваются целиком. То же правило решает
  вытеснение (`dominates`) при равных последнем шаге и произведении.

```
S = [A, B, C] | [A, D, C]
#0 A  #1 B  #2 D  #3 C    ✓ S из #0 #2 #3: шаги позже, чем у #0 #1 #3
```

### Шаг 2. [x] Копия вместо перехода, повторы, cooldown

Решения: Р3, Р4.

- `engine.py`, копия: совпадение, прошедшее по ребру, остаётся и в старой вершине.
- `engine.py`, склейка в вершине: из двух совпадений остаётся то, у которого больше
  пара (позиция первого шага, позиция последнего шага). Новое совпадение начинается не
  раньше старого и всегда свежее.
- Повторы:
  - Движок помнит позиции токенов, использованных срабатываниями каждого сценария.
  - Срабатывание, у которого есть общая позиция с уже использованными для этого
    сценария, не выдаётся. Само совпадение при этом живёт дальше по своим правилам.
  - Позиции меньше самой ранней позиции начала среди активных совпадений можно
    забывать.
- `cooldown`:
  - В `rules.py` это ключ сценария: ≥ 0, конечное, по умолчанию 0.
  - Срабатывание не выдаётся, если время его последнего шага минус время последнего
    выданного срабатывания этого сценария меньше `cooldown`.
  - Невыданные срабатывания cooldown не продлевают.
- Обновить докстринг `Engine` и README: формулировка «переводит, а не копирует» больше
  не верна.
- Примеры:
  - в `alarm.txt` группа `<дверь> <шаги> <громкий звук>` теперь даёт оба сценария;
  - добавить «выключи свет свет» — одно срабатывание;
  - добавить три `<стекло разбилось>` подряд при `cooldown` у «взлома» — одна тревога.
  - Сделано так: у «взлома» в `smart_home.json` cooldown 60 с, поэтому группы в
    `alarm.txt` разнесены больше чем на минуту. «Выключи свет свет» и «включи чайник и
    свет в спальне» лежат в новом `examples/repeats.txt` (решение пользователя), чтобы
    вывод `stream.txt` не менялся.
- Проверка:
  - `stream.txt` и `pause.txt` дают прежний вывод;
  - «включи чайник и свет в спальне» даёт оба сценария.
  - Сценарии и их порядок прежние, но последняя строка меняется: в конце активных
    совпадений 4 и 1 вместо 0. Копии ждут в вершинах, пока их не снимет пауза больше

### Шаг 3. [x] Задержки между шагами

Решения: Р5, Р6.

- `rules.py`:
  - Шаг шаблона — строка или объект `{"token": ..., "max_gap": ...}`.
  - `max_gap` у первого шага — ошибка.
  - Добавить `max_gap` у сценария.
  - В `engine.py` уже есть `Step(position, event)`, поэтому модель шага шаблона назвать

- `graph.py`:
  - Ключ ребра — токен плюс действующая задержка (уже с учётом сценария и корня).
  - Пришедший токен проверяется на всех рёбрах с этим токеном.
  - `render` показывает задержку у рёбер, где она отличается от корневой.
- `engine.py`:
  - Убрать общий сброс по паузе; проверку, что время не убывает, оставить.
  - Переход по ребру разрешён, если время токена минус время последнего шага совпадения

    Внутреннее ребро — `Edge(token, max_gap)`, задержка у него всегда число.
  - Одинаковые шаблоны внутри сценария сравниваются по токенам и действующим задержкам.

  - Сценарии и их порядок во всех потоках прежние. Последняя строка `stream.txt`:

### Шаг 4. [x] Порог уверенности токена

Решение: Р7, первая часть.

### Шаг 5. [x] Общая уверенность

Решение: Р7.

- `rules.py`: `min_confidence` в корне (обязателен, [0, 1]) и у сценария.
- `engine.py`:
  - Совпадение хранит произведение score (или сумму логарифмов) и число шагов;
    уверенность — их среднее геометрическое.
  - Срабатывание выдаётся, если уверенность не ниже `min_confidence` сценария.
  - `Match` получает поле с уверенностью.
- Ранний отсев по оценке сверху (Р7): для каждой вершины заранее посчитать достижимые
  сценарии — их длину и порог.
- Вершина хранит набор несравнимых совпадений (Р7) вместо одного. Правило склейки из
  шага 2 заменяется доминированием: позиция последнего шага ≥ и произведение ≥.
- `cli.py`: выводить уверенность срабатывания с двумя знаками.
- Пример: две `<дверь>` из Р7.
- Проверка: `stream.txt` даёт прежние 8 сценариев, теперь с уверенностями.
- Сделано так:
  - Частичное совпадение — `Partial(steps, product)` в `engine.py`: `confidence` —
    среднее геометрическое, `bound(L)` — оценка сверху для шаблона длины L. Порог
    сценария считает `RuleSet.confidence_threshold(scenario)`: сценарий, потом корень.

    закрыт недочёт шагов 2–4: какое из двух завершившихся на одном событии совпадений
    выдать, решал порядок обхода.

  - Примеры лежат в новом `examples/confidence.txt`. Две `<дверь>` из Р7 сдвинуты под

### Шаг 7. [ ] Отсутствие события и таймер

Решение: Р9.

- `rules.py`: шаг-тишина `{"absent": [токены], "for": секунды, "min_score": ...}`.
  Он не может быть первым шагом и бывает только в `sequence`. Токены должны быть в
  словаре, `for` > 0.
- Ядро `engine.py`, шаг-тишина:
  - Совпадение дошло до шага-тишины после шага в момент t и ждёт до t + `for`.
  - Запрещённый токен со score не ниже порога и временем в [t, t + `for`] снимает
    совпадение.
  - Когда движок узнаёт, что время больше t + `for` (от события или из `advance`), шаг
    выполнен. Если это последний шаг, сценарий срабатывает. Иначе совпадение идёт
    дальше, и временем последнего шага считается t + `for`.
  - Шаг-тишина в среднее геометрическое не входит.
- Время и сроки:
  - `advance(t)` двигает время без события и возвращает срабатывания. Если t меньше
    последнего времени — ошибка.
  - `push` сначала закрывает окна, истёкшие до времени события.
  - `next_deadline()` возвращает ближайший срок или `None`.
- Тишина до предыдущего шага: запрещённый токен незадолго до двери тоже нарушает
  тишину. Для этого движок помнит последние появления токенов.
- Таймер-поток — отдельный модуль или класс поверх `Engine`:
  - одна блокировка на `push` и `advance`;
  - поток ждёт `next_deadline()` по часам (Unix time) и просыпается раньше, если `push`
    сдвинул ближайший срок;
  - поток вызывает `advance(time.time())`;
  - в живом режиме все срабатывания отдаются через callback, вызывать его вне
    блокировки.
- `cli.py`: прогон файла идёт без потока; строка-метка времени в файле потока вызывает
  `advance`.
- Открытые вопросы, задать пользователю до реализации:
  - длина окна «до» предыдущего шага (предложение: то же `for`);
  - формат строки-метки времени (предложение: строка из одного числа);
  - закрывает ли конец файла открытые окна (предложение: нет, только явная метка).
- Примеры:
  - оба сценария из Р9;
  - разрез потока на порции в любом месте, в том числе внутри окна тишины, даёт тот же
    результат.

### Дополнение. [x] Ускорение прохода

По просьбе пользователя: событие трогает только то, что ждёт его токен. Раньше `push` на любом
токене обходил все активные совпадения и все рёбра их вершин и заново собирал `active`. Решение
Р10 (бор вместо Ахо–Корасика) не меняется, порядок выдачи и ничья — Р16.

- `domain/graph.py`: у `Node` есть `max_gap` (наибольшая задержка рёбер) и `floor`. Ранний отсев
  `product ** (1 / L) >= threshold` хоть для одного шаблона из `ahead` равносилен
  `product >= min(threshold ** L)`, поэтому вдали от границы хватает одного сравнения, а рядом с
  ней проверяется прежняя формула. `insert_scenario` возвращает созданные рёбра.
- `domain/unordered.py`: `Unordered.groups()` — группы одинаковых шагов с маской номеров.
  Закрытые шаги набора — битовая маска, а шаг, который закроет событие, — младший бит.
- `domain/engine.py`:
  - Индексы «токен → рёбра из корня», «токен → рёбра бора», «токен → шаблоны `any`».
  - `Front`: совпадения одного места по возрастанию последнего шага, произведение у них строго
    убывает. Новое совпадение вытесняет хвост, сроки истекают с головы, а в задержку ребра
    укладывается хвост, найденный двоичным поиском. В вершину за событие входит одно
    совпадение — лучшее, первое в этом хвосте. Отсеянные и, у конечной вершины, все
    продолжения перебираются как прежде.
  - Очередь сроков (куча) снимает истёкшие совпадения. Снятие проверяется прежней формулой.
  - `_taken` чистится, когда с прошлой чистки прошло не меньше событий, чем совпадений и
    запомненных позиций.
  - `Miss`, `Waiting`, `snapshot`, `misses` и публичное API не менялись.
- Проверено на 8000 случайных наборов правил и потоков (альтернативы, `any` с повторами и
  разными порогами, пороги и задержки шагов, cooldown, `add_scenario` посреди потока,
  токены вне словаря) против движка из `main`. Совпали срабатывания, все отказы, снимок и
  `active_count`; отличается только порядок срабатываний одного события, теперь по Р16.
  Вывод `cli run` на всех девяти потоках `examples/` совпал побайтно. Кадры веб-прогона
  совпали с точностью до порядка строк в таблице ожидания и в отказах: совпадения одной
  вершины теперь идут от старых к свежим, снятия по сроку — первыми.
- Замер (мкс на событие, до → после): токен вне шаблонов при 4000 ждущих совпадениях
  9577 → 2; случайный поток, 800 сценариев, 3617 ждущих: 8615 → 575; 200 сценариев + 100 `any`:
  8130 → 393; 400 совпадений в одной вершине: 17574 → 5.1; `smart_home.json` + `stream.txt`:
  13.5 → 8.8.
- Тесты в `tests/` не менялись.
