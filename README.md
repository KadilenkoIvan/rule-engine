# rule-engine

Быстрый и объяснимый слой поиска голосовых команд и объектов, который стоит
**перед** языковой или визуальной моделью, и движок правил на конечных автоматах,
который безопасно исполняет найденные команды: с таймаутами, повторами и
откатами. LLM, VLA и TTS не используются. Есть словарь команд, размеченные
запросы, автоматы устройств и динамическое программирование там, где оно
даёт выигрыш.

```
«выкючи свет в спальне»
  → нормализация → каскад поиска (точно → основа → префикс → опечатка, DP)
  → k-best разбор фразы (DP) → гипотезы «действие + цели» → политика безопасности
  → план по рёбрам автоматов (DP-кратчайший путь) → исполнение (повторы, сверка, сага)
  → «Готово: выключить свет в спальне, ночник» + объяснение каждого шага
```

## Быстрый старт

```bash
uv sync                      # Python ≥ 3.12, зависимостей нет
uv sync --extra morph        # опционально: pymorphy3 (--stemmer pymorphy)

uv run rule-engine query "выкючи свет в спальне"            # понять без исполнения + объяснение
uv run rule-engine run --file examples/demo.txt -v --state  # демо-диалог в симуляторе
uv run rule-engine repl --room kitchen                      # интерактивно (:help)
uv run rule-engine rules                                    # скомпилированные правила и предупреждения
uv run rule-engine eval --typos 2 --ablation --scaling --antonym-stress --report docs/REPORT.md
uv run rule-engine mine src/rule_engine/data/logs.jsonl --min-support 0.25 --apply
uv run pytest                                               # 140 тестов
```

Пример с отказом устройства и откатом:

```bash
uv run rule-engine run "включи свет на кухне и включи телевизор" --inject living_tv:fault -v
# [ROLLED_BACK] Не получилось (Неисправность устройства…). Все изменения откатил.
```

## Как идеи тимлида легли на код

| Идея | Где реализовано |
|---|---|
| **1. Стейт-машина** | `fsm.py`: автоматы устройств (лампа off↔on, манипулятор parked→ready→holding, пылесос docked/cleaning/paused) и автомат обработки запроса `RECEIVED → … → SUCCEEDED / ROLLED_BACK` (`engine.py`). Запрос не может пропустить этап: каждый переход проверяется. |
| **«Как ходить по ребру»** | `executor.py`, протокол из пяти фаз: **GUARD** (условие ребра) → **READ** (реальное состояние) → **SEND** (с таймаутом) → **VERIFY** (сверка) → **COMMIT** (переход + журнал отката). Если нужного ребра нет из текущего состояния, планировщик ищет кратчайший путь по автоматическим рёбрам: «возьми чашку» при спящем манипуляторе превращается в «включить → взять». |
| **«Что считать ошибкой»** | `errors.py`, таблица `POLICIES`: каждая ошибка имеет код, этап, признак «временная» и стратегию (CLARIFY / CONFIRM / REJECT / RETRY / REPLAN / ROLLBACK / SKIP / ALERT). Повторная команда «включи свет» — не ошибка, а идемпотентный no-op. Таймаут — не неудача, а неизвестный исход: сначала читаем состояние. |
| **2. Задержки, ошибки, откаты** | Повторы с экспоненциальным backoff и джиттером; число попыток каждому шагу выделяет DP-«рюкзак» под общий дедлайн; сверка после таймаута (команда могла примениться с опозданием); перестроение пути при STATE_DRIFT; сага с компенсацией в обратном порядке (путь назад по автомату — DP, значения восстанавливаются); некритичные шаги сценария дают PARTIALLY_SUCCEEDED; команда «отмени» откатывает последний запрос. |
| **3. Движок принимает набор и составляет набор правил** | `rules.py`: из спецификации компилируются правила LEXICAL, TRANSITION, APPLICABILITY, SAFETY, COMPENSATION, SCENARIO и **автоматически найденные** CONFUSABLE (опасно похожие синонимы разных действий, «включи» ~ «выключи», d=1). Плюс статический анализ: недостижимые состояния, конфликты синонимов, рёбра без пути отката. `mining.py`: из журнала команд (в том числе сырых текстов) выводятся сценарии-привычки и правила «после A обычно B». |
| **Поток команд → сценарий** | `stream.py`: потоковое выравнивание Смита–Уотермана (DP, O(шагов) на событие) потока выполненных команд с шагами сценариев. Движок замечает, что пользователь вручную проходит «Ухожу из дома», и предлагает выполнить остальное. Ответ «да» запускает сценарий, событие-антоним снимает засчитанный шаг. |

## Где используется динамическое программирование

| # | Задача | DP | Файл |
|---|---|---|---|
| 1 | Опечатки | Взвешенное расстояние Дамерау–Левенштейна (OSA): соседние клавиши ЙЦУКЕН и фонетически близкие буквы дешевле, перестановка 0.7, ранний выход по порогу | `text/distance.py` |
| 2 | Нечёткий поиск по словарю | Строки таблицы Левенштейна считаются по префиксному дереву: общий префикс — общая строка DP, ветки с `min(row) > порог` отсекаются | `index/fuzzy.py` |
| 3 | Разбор фразы на синонимы | k-best сегментация (Витерби с лучом): «свет на кухне» как имя устройства *и* как «свет» + «кухня» доживают до ранжирования | `parser.py` |
| 4 | Путь по автомату | Беллман–Форд по числу рёбер (`best[k][s]`), с guard'ами и ограничением длины; тот же DP строит путь отката | `fsm.py` |
| 5 | Повторы под дедлайн | Рюкзак с выбором: `best[i][b] = max_k best[i−1][b−cost_i(k)] + log(1−(1−p_i)^k)`, вероятности успеха онлайн обновляются (Beta) | `planner.py` |
| 6 | Сценарий в потоке | Потоковый Смит–Уотерман с битовой маской покрытых шагов | `stream.py` |
| 7 | Майнинг привычек | Вхождение подпоследовательности с ограничением на разрыв: `reach[k][i]` + префиксные суммы. Жадный алгоритм здесь неверен, есть тест-контрпример | `mining.py` |

Оптимальность DP проверяется тестами против полного перебора: распределение
попыток, вхождение с разрывом, эквивалентность всех бэкендов нечёткого поиска.

## Ответы на «что решить команде»

### 1. Какие преобразования текста допустимы

**Разрешены** (не меняют смысл): NFKC, нижний регистр, `ё → е`, пунктуация,
исправление раскладки (`dsrk.xb → выключи`, только если результат есть в
словаре), числительные (`двадцать два → 22`, в том числе с опечаткой
`двпдцать`), основа слова. Основа хранится *рядом* со словом, а не вместо него.

**Запрещены**:
- удаление отрицаний: «не включай свет» → отказ, а не «включи свет»;
- удаление чисел;
- удаление приставок: «в-ключи» и «вы-ключи» — разные основы, стеммер режет только окончания;
- нечёткое сопоставление служебных и коротких слов: «на» не должно стать «но».

Каждое преобразование попадает в `trace` и видно в объяснении.

### 2. Неоднозначность и безопасный отказ

Безопасный отказ — любой исход, кроме *молчаливого выполнения неверной
команды*: REJECT, NOT_FOUND, CLARIFY (варианты), CONFIRM (да/нет). Политика —
упорядоченные правила (`policy.py`), сработавшее правило попадает в ответ:

| Правило | Что делает |
|---|---|
| P2 | отрицание → отказ |
| P3 | нет ни одного точного совпадения и есть нераспознанные слова → «не понял» (не переспрашиваем про «какая погода») |
| P4 | значение вне диапазона / несовместимое действие → отказ |
| P5 | нечётко распознанный глагол почти так же близок к **антониму** → «Включить или выключить?» |
| P6 | не хватает действия, цели или значения → вопрос по существу («В какой комнате?», «Какое значение (от 1 до 100)?») |
| P7 | второй вариант в пределах margin → уточнение |
| P9 | высокий риск → подтверждение; опечатка в команде выше среднего риска → подтверждение |

Ещё один **гейт риска на уровне плана**. «Нагрей духовку до 200» сама по себе
средней опасности, но духовка выключена, и план вставляет ребро «включить
духовку» (высокий риск), поэтому движок попросит подтверждение. Риск
оценивается по реально проходимым рёбрам, а не по словам.

Порог `antonym_margin = 0.7` подобран стресс-тестом: все однобуквенные опечатки
глаголов с антонимами, 2440 запросов. Это минимальный порог с нулём
молчаливых антонимов плюс запас:

| antonym_margin | верно выполнено | выполнен антоним | переспросили |
|---|---|---|---|
| 0 (правило выкл.) | 98.3% | 0.08% (2) | 1.5% |
| 0.6 | 98.0% | 0 | 2.0% |
| **0.7** | 96.1% | **0** | 3.8% |
| 1.5 | 75.4% | 0 | 24.5% |

### 3. Качество, задержка и размер индекса

Полные таблицы — в [`docs/REPORT.md`](docs/REPORT.md). Главное:

**Основной прогон**: 149 размеченных запросов и 184 сгенерированные опечатки,
всего 333; бэкенд trie, встроенный стеммер.

| P@1 | Recall@3 | MRR | точность решения | молча неверно | молча опасно | лишние уточнения | p50 | p95 | p99 | индекс | сборка |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 0.984 | 1.000 | 0.992 | 1.000 | 0 | 0 | 0 | 0.8 мс | 2.1 мс | 3.0 мс | 540 КБ | 30 мс |

P@1 < 1 только из-за запросов, где правильный ответ — уточнение, и эталон
стоит вторым вариантом в списке. Задержка — понимание запроса (нормализация →
решение) на чистом Python.

**Абляции**, что даёт каждый компонент:

| конфигурация | P@1 | точность решения | молча неверно | молча опасно |
|---|---|---|---|---|
| только точное совпадение | 0.541 | 0.808 | 1.2% | 0 |
| + основа | 0.554 | 0.823 | 1.2% | 0 |
| + префикс | 0.574 | 0.844 | 1.2% | 0 |
| **полный каскад** (+ опечатки) | **0.984** | **1.000** | **0** | **0** |
| без подтверждения риска | 0.984 | 0.916 | 8.4% | **28** |
| без правила отрыва (margin) | 0.984 | 0.982 | 1.8% | 0 |
| без политики безопасности | 0.984 | 0.883 | 12.3% | **31** |

Поиск отвечает за то, *найдена ли* команда, политика — за то, *можно ли её
молча выполнить*. На датасете правило антонимов подстраховано правилом отрыва,
но стресс-тест выше показывает его самостоятельный вклад.

**Масштабирование**: синтетические словари, 200 запросов «включи <имя>», в
половине из них опечатка.

| устройств | бэкенд | индекс | сборка | p50 | p95 | P@1 |
|---|---|---|---|---|---|---|
| 1 000 | trie | 2.9 МБ | 44 мс | 2.7 мс | 6.6 мс | 0.99 |
| 1 000 | symspell | 16.6 МБ | 165 мс | 1.4 мс | 2.3 мс | 0.99 |
| 10 000 | trie | 20 МБ | 0.4 с | 7.7 мс | 15.5 мс | 0.94 |
| 10 000 | symspell | 112 МБ | 1.8 с | 6.5 мс | 9.7 мс | 0.94 |
| 10 000 | ngram | 25 МБ | 0.5 с | 12.8 мс | 37.7 мс | 0.94 |
| 10 000 | перебор (baseline) | 15.5 МБ | 0.5 с | 71 мс | 176 мс | 0.94 |

Выбор по умолчанию — **trie**. По качеству все бэкенды эквивалентны (это
проверено тестом), а trie даёт задержку в пределах десятков миллисекунд при
индексе в 5 раз меньше SymSpell. SymSpell оправдан, когда важен хвост задержки
и память не ограничена. Падение P@1 на 10k — это коллизии синтетических имён
(«калимо» / «калино»): движок в таких случаях переспрашивает (Recall@3 = 0.995)
и не выполняет молча.

## Сценарии пользователя из задания → тесты

| Сценарий | Проверка |
|---|---|
| Точное и неполное название возвращает ожидаемое устройство | категории `exact`, `partial` датасета, P@1 = 1.0; `test_cascade_levels`, `test_multiword_alias_and_deep_second_pass` |
| Синоним и опечатка не приводят к молчаливому выбору опасной команды | `dangerous_silent = 0` на датасете и опечатках; `test_dangerous_commands_with_typos_are_never_ok`; стресс-тест антонимов; абляция `no-risk-confirm` показывает 28 молчаливых опасных выполнений без политики |
| После добавления синонима результаты меняются без порчи старых записей | `test_added_synonym_changes_only_target_queries`: регрессия на всём датасете, изменился ровно один целевой запрос; откат версии возвращает поведение; `rule-engine add-alias` печатает дифф регрессии; конфликт синонимов ведёт к уточнению, а не к перезаписи |

## Устройство

```
src/rule_engine/
  text/normalize.py   нормализация, раскладка, числительные, токены (отрицание/союз/квантор/служебные)
  text/stem.py        стеммер без отрезания приставок; опционально pymorphy3
  text/distance.py    взвешенный Дамерау–Левенштейн (DP)
  index/fuzzy.py      бэкенды: trie (DP по дереву) | symspell | ngram | brute
  index/lexicon.py    каскад EXACT→LAYOUT→STEM→PREFIX→FUZZY, многословные синонимы, версии, откат
  spec.py             модель данных и валидация словаря
  rules.py            компилятор правил + статический анализ + опасно похожие пары
  parser.py           k-best сегментация (DP), подкоманды по союзам («выключи свет и телевизор»)
  resolver.py         гипотезы: тип/устройство/комната/контекст/квантор/объекты сцены; объяснимый скоринг
  policy.py           правила решения OK/CLARIFY/CONFIRM/REJECT/NOT_FOUND
  fsm.py              автоматы, история переходов, DP-путь
  planner.py          план по рёбрам, идемпотентность, авто-шаги, DP-распределение попыток
  executor.py         протокол прохода по ребру, симулятор устройств, повторы, сага, отмена
  world.py            состояние мира (убеждение движка), сцена детектора
  engine.py           конвейер-автомат, диалог (уточнение, подтверждение, «везде», «второй», «сорок»), синонимы
  stream.py           распознавание сценария в потоке команд (DP)
  mining.py           выучивание привычек и правил следования (DP)
  evaluation.py       метрики, опечатки, абляции, масштабирование, стресс-тест, регрессия
  cli.py              командная строка
  data/spec.json      словарь: 7 комнат, 12 действий, 13 типов устройств, 24 устройства, 4 типа объектов, 5 сценариев
  data/queries.jsonl  149 размеченных запросов в 16 категориях
  data/logs.jsonl     пример журнала для майнинга
```

### Скоринг — без чёрного ящика

```
score = 0.45·качество_глагола + 0.25·качество_цели + 0.2·покрытие + 0.1·частота − штрафы
```

Качество совпадения: точное 1.0, раскладка 0.97, основа 0.95, префикс 0.6–0.9,
опечатка `0.9 − 0.25·d`. Штрафы: разбор хуже лучшего (пропустил распознанное
слово), устройство не в названной комнате, названная цель не подходит действию.
Каждое слагаемое печатается в объяснении (`rule-engine query … --explain`).

### Мультимодальность

Объекты сцены приходят от детектора (`Engine.update_scene`, в REPL
`:scene [...]`) с типом, атрибутами (цвет, положение, размер) и уверенностью.
«Возьми красную чашку» → тип `cup` + атрибут `color=red` → объект сцены, а
исполнитель — манипулятор. Если чашек две, движок спросит «Какой объект
взять?», и можно ответить «красную» или «второй». Объект с уверенностью
детектора ниже 0.5 не пройдёт guard `object_visible`. Объект в захвате не
исчезает из мира, даже если детектор его больше не видит.

## Форматы данных

- **`spec.json`** — комнаты, действия (синонимы, риск, антоним, нужно ли
  значение), типы устройств с автоматами (рёбра: `action`, `from`, `to`,
  `risk`, `auto`, `guard`, `range`, `value`, `irreversible`), устройства
  (параметры симуляции: задержка, доля сбоев), объекты сцены, атрибуты,
  сценарии (шаги с `critical`), настройки политики и исполнения. Синоним
  действия может нести подсказку типа: «поставь на охрану» → `turn_on` для
  `alarm`.
- **`queries.jsonl`** — `{"q", "cat", "expect": "OK|CLARIFY", "action", "targets", "objects", "scenario", "value", "room"}`.
- **`overlay.json`** — версионированные дополнения: синонимы
  (`add-alias`/`rollback-alias`) и выученные сценарии (`mine --apply`).
  Исходная спецификация не меняется.
- **`logs.jsonl`** — `{"session"?, "ts", "text"}` или `{"session"?, "ts", "action", "device"}`.

## Ограничения

- Ошибка, дающая другое словарное слово («выключи» → «включи»), на
  лексическом уровне неотличима от правильной команды. Защита — подтверждение
  опасных команд. Генератор опечаток такие случаи исключает и считает отдельно.
- Скорость указана для чистого Python. Узкое место по профилю — DP-строки
  нечёткого поиска и сборка гипотез; оба переносятся на компилируемый язык без
  изменения алгоритмов.
- Устройства симулируются (`SimulatedDriver`). Для реальных достаточно
  реализовать протокол `Driver` (`send`, `read_state`).
- Датасет размечен вручную одним автором; для серьёзных выводов нужна
  независимая разметка и реальные (в том числе ASR) запросы.
