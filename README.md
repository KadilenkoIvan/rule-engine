# Проект Rule engine

Движок правил, например для умного дома. На вход подаётся поток токенов (слов, команд или звуковых сигналов) с уверенностью детектора и временем, а на выходе получаются сработавшие сценарии.

## Постановка задачи

На вход идёт поток токенов: слова команд ("включи", "свет") и звуковые сигналы (<дверь>, <стекло разбилось>). У каждого токена есть уверенность детектора (score) и время. Правила описывают сценарии: "включи свет в ванной", "взлом" = <дверь> и <громкий звук> в любом порядке, "хозяин пришёл" = <дверь>, после которой 3 с тихо. Движок читает поток по одному событию и сообщает, какие сценарии сработали.

### Сложности задачи:

* между нужными токенами бывают лишние ("включи, пожалуйста, свет")
* лишний токен может оказаться шагом другого сценария
* у сценариев общие начала, и сработать на одном потоке могут несколько
* шаги ограничены по времени
* токены бывают неуверенными
* отсутствие события в течение какого-то времени тоже может являться событием
* нужно создать решение оптимальное по памяти и времени 

## Последовательность работы решения

1. Правила. JSON превращается в RuleSet. Каждому шагу сразу проставляются его задержка max_gap, порог min_score и прочие настройки. 
2. Граф. Сценарии с порядком шагов складываются в сжатый бор, сценарии, которые срабатывают из определенных токенов в любом порядке хранятся в отдельном списке наборов.
3. Проход. ``push(event)`` продвигает частичные совпадения, ``advance(t)`` двигает время без события (нужно, чтобы закрылось окно тишины). Оба возвращают сработавшие сценарии.
4. Объяснения. Попутно движок хранит причины, по которым тот или иной сценарий не прошел до конца. Например, почему токен ничего не сдвинул (порог, опоздание, нарушенная тишина, повтор, cooldown). Записывает их сам движок, чтобы интерфейс не держал второй копии правил прохода.

## Алгоритмы и особенности решения

### 1. Сжатый бор
Шаблоны с общим началом делят вершины. 
"включи свет в ванной" и "включи свет в спальне" расходятся только на последнем шаге.

Каждое ребро содержит в себе токен, задержку и порог. Два сценария делят ребро, только если эти поля у них совпадают. Иначе пришлось бы хранить в одной вершине совпадение, которое одному сценарию ещё годится, а другому уже нет.

### 2. Копия вместо перехода
Совпадение, пройдя по ребру, остаётся и в старой вершине. Без этого лишний токен со своим ребром уводит совпадение в чужую ветку.
Это семантика skip-till-any-match. Возвраты назад по потоку не нужны, поэтому поток можно подавать кусками.

### 3. Почему не Ахо–Корасик? 
Он помнит одно состояние и находит только непрерывные вхождения. Чтобы помнить <дверь> после <шаги>, нужно держать несколько состояний сразу, и тогда суффиксные ссылки уже не нужны.

### 4. Шаблоны "в любом порядке"

Для сценария "взлом", например, неважно, что пришло раньше - дверь или громкий звук. Перестановки в дереве дали бы n! путей, поэтому такие шаблоны живут отдельно. Состояние совпадения хранится как битовая маска.

### 5. Уверенность

В решении используются две проверки:

* Порог токена (min_score). Слабый токен ребро просто не принимает, совпадение ждёт дальше.
* Общая уверенность - это среднее геометрическое score шагов `(s_1·…·s_k)^(1/k)`. Сценарий срабатывает, если она не ниже min_confidence.

Среднее геометрическое выбрано потому, что оно не зависит от длины фразы и не даёт сильному сигналу перекрыть слабый.

### 6. Тишина "ничего не произошло"

Шаг-тишина - особое ребро. Совпадение, дошедшее до него в момент ``t``, открывает окно до ``t + for``. Запрещённый токен в окне снимает совпадение, а если окно прошло чисто, оно идёт дальше.

Окно закрывается, когда время уходит за его конец из-за следующего события или обновления таймера. В live-режиме advance зовёт поток-таймер LiveEngine. Поток спит до ближайшего срока ``next_deadline()``, поэтому "хозяин пришёл" срабатывает через 3 с, даже если больше ничего не пришло.

### 7. Иерархическое колесо таймеров

Концы окон тишины нужно где-то хранить. От хранилища требуются три операции: быстро поставить срок, быстро его отменить (тишину нарушил токен, совпадение снимается очень часто) и при сдвиге времени достать всё, что истекло. Для этого было сделано иерархическое колесо таймеров, как в Kafka.
Колесо - это несколько уровней по 64 ячейки. На уровне 0 ячейка шириной 0.01 с (тик), на каждом следующем уровне ячейка в 64 раза шире предыдущей. Ячейка хранит список таймеров, срок которых попадает в её отрезок времени.
`advance(now)` проходит ячейки, время которых прошло. Каждый таймер из них ставится заново: если срок прошёл, таймер сработал, иначе он спускается уровнем ниже, где ячейки мельче.
Операция отмены `cancel` только ставит таймеру флаг, а из ячейки отменённый таймер выбрасывается, когда до неё дойдёт разбор (ленивая отмена). 

Операции
* Поставить, отменить	О(число уровней), на практике O(1)
* Обновить advance	O(64 · уровней + таймеров в разобранных ячейках)
* next_deadline	O(64 · уровней + размер ячейки)

### 8. Повторы и cooldown

Из-за копий сценарий мог бы сработать дважды на одних и тех же токенах ("выключи свет свет"). Поэтому срабатывание, у которого есть общий токен (по номеру в потоке) с уже выданным срабатыванием этого сценария, не выдаётся. Из совпадений одного сценария, завершившихся одновременно, выдаётся самое уверенное. Сработавший сценарий молчит заданное время.

### 9. Режим поправок

Флаг self_correction включает отложенную выдачу. Сработавший сценарий ждёт заданное количество секунд, и за это время токен исправления (например, "ой") его снимает, а "не" перед командой её подавляет: "включи свет в ванной, ой, в спальне" выдаёт только спальню.

## Другие оптимизации

### Меньше совпадений

1. В одном месте могут ждать несколько совпадений. Совпадение A вытесняет B, если A не старее (последний шаг не раньше) и не менее уверенно (произведение score не меньше). Остаются только несравнимые - свежее против более уверенного. Это фронт Парето по двум осям. Искусственного предела на число совпадений нет, т.к. всё, что осталось, ещё может пригодиться.

2. Совпадение выбрасывается сразу, если даже при score 1.0 у всех оставшихся шагов оно не дотянет до порога ни одного сценария ниже по дереву. 

3. Совпадение, у которого истекли задержки всех следующих рёбер, снимается. Посторонние токены срок не продлевают.

### Меньше работы на событие

1. Событие не обходит всех ждущих, а смотрит только тех, кто ждёт именно его токен. Посторонний токен вроде "пожалуйста" почти ничего не стоит при любом числе ждущих совпадений.
2. Фронт (все частичные совпадения, которые ждут в одном месте) хранится как отсортированный список. После вытеснения совпадения одного места лежат по возрастанию времени последнего шага, а произведение у них строго убывает.
3. Сроки max_gap лежат в куче, по записи на фронт. Событие снимает только то, что действительно истекло, а не проверяет каждое совпадение.

### Меньше памяти

1. Сжатый бор (radix trie). Цепочка рёбер без развилок и завершений хранится одним сегментом, а совпадение указывает на позицию внутри него. При добавлении сценария, который разветвляется внутри сегмента, сегмент расщепляется, а ждущие совпадения переносятся без потерь.
2. Совпадение хранит не кортеж всех шагов, а последнее звено ``History(step, previous)``. Продолжение - это одно новое звено за O(1), копии делят общий префикс. Полный список шагов собирается только для результата.
3. Номера токенов, уже вошедших в срабатывания, нужны для проверки повтора. Чистятся они реже, чем на каждом событии, но так, что в среднем это O(1) на вызов и память не растёт на длинном потоке.

## Замеры

Сравниваются две версии движка с одинаковым результатом:

1. Полный обход. Каждое событие перебирает все ждущие совпадения подряд и у каждого проверяет, подходит ли токен.
2. Текущая версия с ускорениями: индексы по токену (событие сразу находит тех, кто ждёт именно его), отсортированные фронты и очередь сроков.

| Нагрузка | Полный обход | Индексы |
|---|---:|---:|
| 40 цепочек по 40 шагов с посторонними токенами | 113.6 | 5.7 |
| 800 сценариев, ждут многие | 1053.0 | 8.0 |
| 400 совпадений в одной вершине | 53 931.5 | 5.8 |
| 200 сценариев с окнами тишины | 158.4 | 64.4 |
| 100 наборов с `any` / `any_vac` | 3219.2 | 1249.9 |
 
Меньше всего выигрывают наборы с шагом `any`: такой шаг ждёт любой токен, и почти каждое
событие продвигает их все.

## Использование

### Установка

```bash
uv sync
```

### Выбор интерфейса

```bash
uv run rule-engine cli …   # командная строка
uv run rule-engine web …   # веб-интерфейс
```

### Командная строка

```bash
uv run rule-engine cli graph examples/smart_home.json                     # граф сценариев
uv run rule-engine cli run examples/smart_home.json examples/stream.txt   # прогнать поток
```

`graph` печатает граф деревом, `run` - строку на каждое срабатывание и число
незавершённых совпадений в конце. 

### Веб-интерфейс

```bash
uv run rule-engine web examples --host 0.0.0.0 --port 9000
```
